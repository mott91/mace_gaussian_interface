# Domain Pitfalls: v1.2 Analysis Quality Overhaul

**Domain:** IR spectroscopy analysis pipeline improvements
**Researched:** 2026-03-28

## Critical Pitfalls

### Pitfall 1: NistChemPy is a Web Scraper, Not an API

**What goes wrong:** NistChemPy works today, breaks next month when NIST changes their HTML layout. Your automated experimental comparison pipeline silently fails, or worse, returns wrong data from a different compound.

**Why it happens:** NIST Chemistry WebBook has NO official API. NistChemPy parses HTML pages. Any change to NIST's web frontend -- new CSS classes, layout changes, URL structure updates -- breaks the scraper. NIST has no obligation to maintain backward compatibility for scrapers.

**Consequences:** Experimental comparison feature becomes unreliable. Tests that depend on NIST access fail intermittently. Thesis appendix with "automated NIST comparison" becomes embarrassing if it doesn't work during the defense.

**Prevention:**
1. **Cache everything locally.** After first successful fetch, save JCAMP-DX files to `experimental_spectra/{cas_number}.jdx`. Never re-fetch unless explicitly asked.
2. **Decouple fetch from analysis.** `fetch_experimental.py` is a separate CLI command, not called automatically during analysis. User runs `mace-gaussian fetch-experimental water` once, then analysis reads from cache.
3. **Pin NistChemPy version** in pyproject.toml. Don't auto-upgrade.
4. **Graceful degradation.** If NIST fetch fails, log a warning and skip experimental comparison. Never crash the analysis pipeline.
5. **Pre-fetch for benchmark set.** Before the benchmark campaign, fetch and cache all experimental spectra. Then analysis runs are offline-safe.

**Detection:** CI test that attempts to fetch water spectrum from NIST (mark as `@pytest.mark.network`). If it fails, you know NistChemPy is broken before it matters.

### Pitfall 2: Transmittance vs Absorbance Unit Confusion

**What goes wrong:** NIST IR spectra are in transmittance (% T). Computed spectra are in absorbance/intensity (km/mol). You overlay them without conversion and get an inverted-looking comparison that means nothing.

**Why it happens:** JCAMP-DX files from NIST use transmittance (100% = no absorption, 0% = full absorption). Computed IR spectra use absorption intensity (0 = no absorption, higher = more absorption). The two are mathematically related but visually opposite.

**Consequences:** Plots that look wrong to any spectroscopist reviewing the thesis. Spectral similarity scores that are meaningless or negative.

**Prevention:**
1. **Always convert to absorbance:** `A = 2 - log10(%T)` or equivalently `A = -log10(T/100)`. Handle T=0 edge case (set to small epsilon).
2. **Normalize both spectra** to [0, 1] range for visual comparison. The absolute scales are different (km/mol vs absorbance units) and cannot be directly compared.
3. **Label axes clearly** in plots: "Normalized Absorbance" for both, with a note that experimental is from NIST.
4. **Unit test** the conversion function with known values.

**Detection:** Visual inspection of first experimental overlay plot. If peaks point in opposite directions, the conversion is wrong.

### Pitfall 3: Lorentzian HWHM vs FWHM Convention Mismatch

**What goes wrong:** You implement Lorentzian with FWHM=4 cm^-1 but the formula uses HWHM (gamma), so the actual linewidth is 2 cm^-1. Or vice versa. Peaks are too narrow or too broad.

**Why it happens:** Two common Lorentzian conventions:
- Physics: `L(x) = (1/pi) * gamma / ((x-x0)^2 + gamma^2)` where gamma = HWHM
- Spectroscopy: `L(x) = (FWHM/2)^2 / ((x-x0)^2 + (FWHM/2)^2)` where FWHM is full width

Papers sometimes say "FWHM=10 cm^-1" but the code uses gamma (HWHM), so you'd need gamma=5.

**Consequences:** Broadened spectra look subtly wrong. Hard to catch because "too broad" and "too narrow" are subjective until you compare to literature.

**Prevention:**
1. **Pick one convention and document it.** Recommend: parameter named `fwhm` in the function signature, internally convert to `gamma = fwhm / 2`.
2. **Verify against known result.** Broaden a single peak at 1000 cm^-1 with FWHM=10 cm^-1. The peak should reach half its maximum value at 995 and 1005 cm^-1. Write a test for this.
3. **Document the formula** with an explicit "FWHM = full width at half maximum = 2*gamma" note.

**Detection:** Unit test that checks FWHM of broadened single-peak spectrum.

## Moderate Pitfalls

### Pitfall 4: Degenerate Mode Subspace Overlap Numerical Issues

**What goes wrong:** The subspace overlap metric `trace(M^T @ M) / k` gives values > 1.0 or < 0.0 due to numerical precision, or gives misleadingly low values when ML splits near-degenerate modes more than the tolerance.

**Prevention:**
1. Clip result to [0, 1] range.
2. Use a generous tolerance for grouping (10 cm^-1 for near-degeneracies in ML, not just 1 cm^-1).
3. Report both individual and subspace overlap so the user can diagnose issues.

### Pitfall 5: NIST Compound Name Ambiguity

**What goes wrong:** Searching NIST for "ethanol" returns multiple results (ethanol, ethanol-d6, etc.). Automated pipeline picks the wrong one.

**Prevention:**
1. Search by CAS number, not by name. Map molecule names to CAS numbers in a lookup table.
2. If using name search, require exact match and verify molecular formula.
3. Log which compound was matched and its CAS number for traceability.

### Pitfall 6: Timing Comparison Unfairness

**What goes wrong:** ML timing includes model loading (one-time cost) while DFT timing doesn't include Gaussian startup. Or DFT timing includes SLURM queue wait while ML runs locally. Apples-to-oranges comparison.

**Prevention:**
1. Separate "setup time" (model loading, Gaussian startup) from "computation time" (actual calculation).
2. Report DFT compute time separately from DFT wall-clock time (which includes queue wait).
3. For fair comparison: use DFT compute time vs ML compute time. For practical comparison: use DFT wall-clock vs ML wall-clock.
4. Report both in the timing table.

## Minor Pitfalls

### Pitfall 7: JCAMP-DX Format Variations

**What goes wrong:** Some JCAMP-DX files use different data encoding (AFFN, DIFDUP, SQZDUP). The `jcamp` library handles most but not all encodings.

**Prevention:** Test with actual NIST downloads for your benchmark molecules before building the pipeline. The `jcamp` library's test suite covers the common encodings.

### Pitfall 8: VPT2 Spike Scope Creep

**What goes wrong:** The "2-hour spike" to test Psience turns into a week-long integration project. You start building a full QCEngine harness or forking Psience to accept Gaussian force constants.

**Prevention:**
1. Time-box strictly: 2 hours. If it doesn't work in 2 hours, shelve it.
2. Success criterion: can Psience produce anharmonic frequencies for water using force constants from Gaussian .fchk? YES/NO.
3. If NO: document what's missing and move on. This is a future-work item, not a v1.2 deliverable.

## Phase-Specific Warnings

| Phase Topic | Likely Pitfall | Mitigation |
|-------------|---------------|------------|
| Lorentzian broadening | FWHM/HWHM confusion (Pitfall 3) | Unit test that verifies FWHM of single peak |
| Zero-intensity filtering | Changing statistics without documenting | Report both filtered and unfiltered metrics |
| Degenerate modes | Tolerance too tight for ML-split degeneracies | Use 10 cm^-1 tolerance, report both metrics |
| NIST comparison | Scraper breaks (Pitfall 1), units wrong (Pitfall 2) | Cache locally, convert to absorbance, test first |
| Timing | Unfair comparison (Pitfall 6) | Separate setup vs compute time |
| VPT2 spike | Scope creep (Pitfall 8) | Strict 2-hour time box |
| Pipeline overhaul | Breaking existing reports while integrating new features | Run regression tests after each integration |
