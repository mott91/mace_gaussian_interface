**Researched:** 2026-03-16
**Domain:** MACE foundation model integration, ASE calculator wiring
**Confidence:** HIGH

## Summary

Phase 13.5 adds MACE-POLAR-1 as a new energy calculator option. This is a well-scoped, pattern-following task: the project already has four MACE calculator branches (`mace_mp`, `mace_off`, `mace_omol`, `mace_anicc`) in `workflow.py::calculator()`, and `mace_polar` follows the same structure with minor API differences. The primary risk is the mace-torch upgrade from 0.3.14 to main branch, since `mace_polar` is not in any PyPI release.

The `mace_polar()` function signature is: `mace_polar(model, device="", default_dtype="float32", return_raw_model=False, **kwargs)`. Model sizes are `"polar-1-s"`, `"polar-1-m"`, `"polar-1-l"` (note: NOT `"small"`/`"medium"`/`"large"` like other MACE calculators). No `dispersion` parameter exists. The function internally sets `model_type="PolarMACE"`. Model auto-downloads on first use like all other MACE foundation models.

**Primary recommendation:** Upgrade mace-torch to main branch, add a `mace_polar` branch to `calculator()` following the established if-chain pattern, and wire it into CLI and DFT baseline config. Total touchpoints: 4 files, ~15 lines of code changes.

## Architecture Patterns

### Integration Points (4 files)

```
mace_gaussian/
├── cli.py              # VALID_ENERGY_CALCULATORS list + click.Choice list
```

### Pattern 1: Calculator Branch in workflow.py
**What:** Add `mace_polar` branch to the `calculator()` if-chain
**When to use:** This is the single established pattern for all energy calculators
**Example:**
```python
# Source: existing pattern in workflow.py lines 285-314
if nnp == "mace_polar":
    from mace.calculators import mace_polar

    calc = mace_polar(model="polar-1-l", device="cuda", default_dtype="float64")
    return calc
```

**Key differences from other calculators:**
- Model size string: `"polar-1-l"` (NOT `"large"` like mace_mp/mace_off)
- No `dispersion=False` parameter (unlike mace_mp/mace_off/mace_omol)
- Takes `model=`, `device=`, `default_dtype=` (like mace_mp/mace_off/mace_omol, unlike mace_anicc)

### Pattern 3: DFT Baseline Entry
**What:** Add `mace_polar` to `DFT_BASELINES` dict in `dft_baseline.py`
**Example:**
```python
# Source: existing pattern in dft_baseline.py lines 50-71
"mace_polar": {
    "method": "b3lyp",
    "basis": "6-31G(d,p)",
    "description": "B3LYP/6-31G(d,p)",
    "extra_keywords": "",

```
Note: Using B3LYP/6-31G(d,p) matching other calculators. The MACE-POLAR-1 paper uses wB97M-V/def2-TZVP as training reference, but that requires newer Gaussian (same situation as mace_omol). B3LYP is the practical DFT baseline for all calculators in this project.

### Anti-Patterns to Avoid
- **Adding mace_polar to default energy calculators:** Would cause failures on machines without main-branch mace-torch. Keep as opt-in.
- **Adding element guard for mace_polar:** 83 elements is broad enough; no guard needed (unlike mace_anicc's HCNO restriction).
- **Passing dispersion=False:** The `mace_polar()` function does not accept a `dispersion` parameter. Passing it would cause a TypeError.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Model downloading | Custom download logic | `mace_polar(model="polar-1-l")` auto-downloads | Upstream handles caching, checksums, URLs |
| Device selection | Manual CUDA detection | Pass `device="cuda"` to constructor | Upstream handles fallback |
| PolarMACE model type | Manual `model_type` kwarg | Let `mace_polar()` set it internally | Function handles this automatically |

## Common Pitfalls

### Pitfall 1: mace-torch Upgrade Breaks Existing Calculators
**What goes wrong:** Upgrading mace-torch from 0.3.14 to main branch could change APIs for mace_mp/mace_off/mace_omol/mace_anicc.
**Why it happens:** Main branch may have breaking changes not yet documented.
**How to avoid:** Run existing test suite after upgrade. Specifically test `calculator("mace_mp")`, `calculator("mace_off")`, `calculator("mace_omol")`, `calculator("mace_anicc")` all still work.
**Warning signs:** ImportError, TypeError on existing calculator calls.

### Pitfall 2: Model Size String Format
**What goes wrong:** Using `model="large"` instead of `model="polar-1-l"`.
**Why it happens:** All other MACE calculators use `"large"`/`"small"`/`"extra_large"` strings. MACE-POLAR-1 uses `"polar-1-s"`, `"polar-1-m"`, `"polar-1-l"` format.
**How to avoid:** Hardcode `model="polar-1-l"` in the calculator branch.
**Warning signs:** Model download fails or wrong model loaded.

### Pitfall 3: Passing dispersion=False
**What goes wrong:** TypeError when calling `mace_polar(dispersion=False)`.
**Why it happens:** Copy-pasting from mace_mp/mace_off/mace_omol branches which all pass `dispersion=False`.
**How to avoid:** Do NOT pass `dispersion` kwarg. Only pass `model`, `device`, `default_dtype`.

### Pitfall 4: ImportError on Older mace-torch
**What goes wrong:** `from mace.calculators import mace_polar` raises ImportError on 0.3.14 or any PyPI release.
**Why it happens:** `mace_polar` only exists on main branch.
**How to avoid:** Let ImportError surface naturally with a clear error message. No version check needed -- the ImportError traceback is self-explanatory. Alternatively, catch ImportError and provide a helpful message pointing to the upgrade command.
**Recommendation:** Let ImportError propagate naturally (consistent with how other import failures work in the project).

### Pitfall 5: First-Run Model Download
**What goes wrong:** First invocation of `mace_polar(model="polar-1-l")` downloads a large model file, which may take time or fail on machines without internet.
**Why it happens:** Same auto-download mechanism as mace_mp/mace_off/mace_omol.
**How to avoid:** Nothing special needed -- this is expected behavior and matches all other MACE calculators.

```python
def _make_import_interceptor_polar(mock_mace_polar):
    original_import = __builtins__.__import__ if hasattr(__builtins__, "__import__") else __import__

        if name == "mace.calculators":
            mock_module = MagicMock()
            mock_module.mace_polar = mock_mace_polar
            return mock_module

class TestCalculatorMacePolar:
```

**MACE-POLAR-1 key properties:**
- Trained on OMol25 (100M structures, wB97M-V hybrid DFT)
- 83 elements supported
- Explicit long-range Coulomb interaction via polarizable multipoles
- Model sizes: polar-1-s (small), polar-1-m (medium, 12A receptive field), polar-1-l (large, 18A receptive field)

## Open Questions

1. **Should mace_polar be added to the default --energy-calculators list?**
   - What we know: Currently defaults to `"mace_mp,mace_omol,mace_anicc,mace_off"`. Adding mace_polar would run it automatically for every molecule.
   - What's unclear: Whether all users will have main-branch mace-torch installed.
   - Recommendation: Do NOT add to defaults. Keep as opt-in via `--energy-calculators mace_polar`. Users who upgrade mace-torch can explicitly request it.

2. **Should charge/spin state be configurable?**
   - What we know: MACE-POLAR-1 supports `atoms.info['charge']` and `atoms.info['spin']` for charged/open-shell molecules.
   - What's unclear: Whether the current pipeline ever handles charged molecules.
   - Recommendation: Defer to future phase. The default neutral/singlet state is correct for all current test molecules. This is a feature enhancement, not a blocker.

3. **Does the mace-torch main branch break the dipole model loading?**
   - What we know: The project uses a custom `mace_dipole_core` package with `torch.load(pickle_module=...)` remapping for the MACE4IR dipole model. The dipole model was saved with older mace class paths.
   - What's unclear: Whether main-branch mace-torch changes internal class paths that affect pickle loading.
   - Recommendation: Test dipole model loading explicitly after upgrade. If it breaks, the `mace_loader.py` pickle_module remapping may need updating.
