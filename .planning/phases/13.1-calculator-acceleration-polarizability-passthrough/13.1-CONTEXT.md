# Phase 13.1: Calculator Acceleration & Polarizability Passthrough - Context

**Gathered:** 2026-03-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Four tightly related improvements to the dipole calculator layer:

1. **Autograd dipole derivatives** — replace 2×3N finite-difference forward passes with a single `get_dielectric_derivatives()` autograd call. Same result, ~20–60x faster.
2. **Polarizability passthrough** — thread real polarizability tensor (currently hardcoded zeros in `write_gaussian_output`) through the pipeline using the value the model already computes.
3. **Raman derivative passthrough** — pass `dalpha_dr` (polarizability Jacobian) through the pipeline to Gaussian's output file. Infrastructure only — Raman analysis in the HTML report is a separate future phase.
4. **Lazy factory instantiation** — don't instantiate all dipole calculators at module import time; instantiate on first `get_calculator()` call.

Raman *analysis* (HTML report, Raman intensity extraction) is explicitly deferred.

</domain>

<decisions>
## Implementation Decisions

### Autograd dipole derivatives
- Override `calculate_dipole_derivatives()` in `MACEDipoleCalculator` (mace_loader.py) to call `self.calc.get_dielectric_derivatives(atoms)` instead of falling through to base class finite differences
- Output reshape: `dmu_dr` comes back as `(3, N_atoms, 3)` → reshape to `(3*N_atoms, 3)` via `dmu_dr.transpose(1, 2, 0).reshape(3*N_atoms, 3)`
- **No silent fallback** — if `get_dielectric_derivatives()` raises (model incompatible, CUDA error, etc.), let the exception propagate loudly. Do not catch and silently fall back to finite differences.
- `MACEMLDipoleCalculator` inherits from `MACEDipoleCalculator` indirectly, so the override propagates automatically without changes to `mace_ml.py`

### Polarizability passthrough
- Add `calculate_polarizability(atoms)` method to `MACEDipoleCalculator` that extracts the static polarizability tensor from the model output
- Thread the value through `calculate_dipole_properties()` in `workflow.py` (currently returns `(dipole, dipole_derivatives, partial_charges)` — expand to include polarizability)
- Update `write_gaussian_output()` in `io.py` to accept and write real polarizability instead of `np.zeros(6)`
- Unit verification is a Claude implementation concern (check model output units vs Gaussian's expected Bohr³)

### Raman derivatives (dalpha_dr) passthrough — infrastructure only
- `get_dielectric_derivatives()` already returns `dalpha_dr` alongside `dmu_dr` when `use_polarizability=True` — extract and thread through pipeline
- Write `dalpha_dr` to the Gaussian external output file (check Gaussian external interface spec for exact format/position)
- **Do not** integrate into HTML report or analysis — that is a separate future phase
- If the model doesn't have `use_polarizability=True`, `dalpha_dr` is unavailable — handle gracefully (zeros or omit, per Gaussian spec)

### Lazy factory instantiation
- Store constructors (callables), not instances, at `DipoleCalculatorFactory.__init__` time
- Instantiate on first `get_calculator(method)` call; cache instance for reuse
- `list_available()` may lazily instantiate all to check availability, or report based on what's been instantiated — Claude's discretion
- `auto` selection path: instantiate in preferred order, stop at first available

### Claude's Discretion
- Unit conversion for polarizability (verify what the model returns, convert to Bohr³ if needed)
- Exact Gaussian external interface format for `dalpha_dr` (position and layout after dipole derivatives block)
- Test coverage approach for the new override and pipeline threading
- Whether `list_available()` triggers instantiation or uses a lighter availability check

</decisions>

<specifics>
## Specific Ideas

- The autograd path and polarizability extraction can share a single `get_dielectric_derivatives()` call — call once, extract `dmu_dr`, polarizability tensor, and `dalpha_dr` all at once rather than calling the model multiple times
- Sanity-check: run autograd and finite-difference paths on water and assert the derivative matrices are close (within numerical tolerance) — either as a formal test or a one-time verification

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `MACEDipoleCalculator` (mace_loader.py) — add `calculate_dipole_derivatives()` override here; `self.calc` is the underlying `MACECalculator_dipole` ASE calculator that exposes `get_dielectric_derivatives(atoms)`
- `DipoleCalculatorBase.calculate_dipole_derivatives()` (base.py) — the finite-difference implementation that the override replaces; keep it in base class for other calculators
- `calculate_dipole_properties()` (workflow.py:105) — needs signature expansion to return polarizability alongside existing returns
- `write_gaussian_output()` (io.py:64) — `polarizability = np.zeros(6)` on line ~95 is the target; expand signature to accept real value

### Established Patterns
- `get_dielectric_derivatives(atoms)` returns `(dmu_dr, dalpha_dr)` tuple when `model.use_polarizability=True`, or just `dmu_dr` otherwise (mace_dipole_core/calculators/mace.py:386–419)
- `dmu_dr` shape: `(3, N_atoms, 3)` — (dipole_component, atom, spatial_dir)
- Required shape for `write_gaussian_output`: `(3*N_atoms, 3)` — (atom*3 + dir, dipole_component)
- Gaussian Fortran-format output uses `D` exponent notation — already handled by existing `line.replace("E", "D")`

### Integration Points
- `mace_gaussian/calculators/mace_loader.py` — primary change: add `calculate_dipole_derivatives()` override to `MACEDipoleCalculator`
- `mace_gaussian/calculators/factory.py` — lazy instantiation refactor; `dipole_factory = DipoleCalculatorFactory()` global stays, but init no longer eagerly constructs calculators
- `mace_gaussian/workflow.py:105` — `calculate_dipole_properties()` return type expansion
- `mace_gaussian/gaussian/io.py:95` — `write_gaussian_output()` signature + polarizability write
